Used Car Price
Predictor

A production-ready REST API that predicts used car prices by combining six market factors: past transactions, competition analysis, vehicle condition, demand trends, new car prices, and depreciation.

Kotlin 1.9 Spring Boot 3.2 MongoDB Gradle (Kotlin DSL) OpenAPI 3 / Swagger JUnit 5 + MockK GitHub Actions CI
Getting started

Overview

This system exposes seven REST APIs covering all six pricing factors plus a unified prediction endpoint. Each factor can be independently populated and queried, and the prediction endpoint aggregates them all in real time to produce a weighted estimated price with a confidence score.

Getting started

Local setup

Prerequisites

Before running the project make sure you have the following installed:

JDK 17+ Required — Spring Boot 3.x requires Java 17 minimum
MongoDB Running on localhost:27017 — use Docker (see below)
Git For cloning the repository
Postman For testing — import the collection from postman/

Start MongoDB via Docker

# Pull and start MongoDB 7 on the default port
docker run -d --name mongodb -p 27017:27017 mongo:7

# Verify it's running
docker ps | grep mongo

# On subsequent restarts just run:
docker start mongodb

Clone and run

git clone https://github.com/hiteshdroid/used-car-price-predictor.git
cd used-car-price-predictor

# Start the Spring Boot server
./gradlew bootRun

The server starts at http://localhost:8080. You should see:

Started CarPredictorApplication in X.XXX seconds (JVM running for X.XXX)

Environment variables

# Override the MongoDB URI (optional — defaults to localhost)
MONGODB_URI=mongodb://user:pass@host:27017/carpredictordb ./gradlew bootRun

# Override the port (optional — defaults to 8080)
PORT=9090 ./gradlew bootRun

Architecture

File by file

Models.kt — six MongoDB documents

Each @Document class maps directly to a MongoDB collection. Spring Data MongoDB handles serialization automatically.

@Document(collection = "transactions")
data class Transaction(
    @Id val id: String? = null,
    val make: String,
    val model: String,
    val year: Int,
    val mileage: Int,
    val salePrice: Double,
    val saleDate: LocalDateTime = LocalDateTime.now(),
    // location, condition, fuelType, transmission, color...
)

DTOs.kt — request and response objects

DTOs are deliberately separated from models so the API contract stays stable even if the database schema evolves. Request DTOs carry @Valid annotations; Spring validates them before the controller body runs.

data class TransactionRequest(
    @field:NotBlank(message = "Make is required")
    val make: String,
    @field:Min(1980) @field:Max(2025)
    val year: Int,
    @field:Positive
    val salePrice: Double,
    // ...
)

data class ApiResponse<T>(
    val success: Boolean,
    val message: String,
    val data: T? = null
)

Repositories.kt — zero-boilerplate queries

Spring Data generates the full query implementation from method names. You declare the interface; Spring writes the MongoDB query at startup.

@Repository
interface TransactionRepository : MongoRepository<Transaction, String> {
    findByMakeAndModel(make: String, model: String): List<Transaction>
    findByMakeAndModelAndYear(make: String, model: String, year: Int): List<Transaction>
}

GlobalExceptionHandler.kt — centralised error mapping

A single @RestControllerAdvice catches all exceptions so no controller needs try-catch blocks. Every error returns a consistent ErrorResponse body.

@ExceptionHandler(NoSuchElementException::class)
fun handleNotFound(ex: NoSuchElementException): ResponseEntity<ErrorResponse> =
    ResponseEntity.status(HttpStatus.NOT_FOUND)
        .body(ErrorResponse(message = ex.message ?: "Resource not found"))

@ExceptionHandler(MethodArgumentNotValidException::class)
fun handleValidation(ex: MethodArgumentNotValidException): ResponseEntity<ErrorResponse> {
    val errors = ex.bindingResult.allErrors.map { it.defaultMessage ?: "Validation error" }
    return ResponseEntity.status(HttpStatus.BAD_REQUEST)
        .body(ErrorResponse(message = "Validation failed", errors = errors))
}
Architecture

Request flow

What happens internally when you call POST /api/v1/predict:

1
HTTP request arrives
Postman sends a JSON body with make, model, year, mileage, condition, location, fuelType, and transmission.
2
@Valid runs on the request body
Spring validates every annotated field. A blank make or a year outside 1980–2025 returns 400 immediately with a per-field error list — before your code runs.
3
PricePredictionController delegates to PricePredictionService
The controller has no logic — it just calls the service and wraps the result in ApiResponse<PricePredictionResponse>.
4
PricePredictionService fans out to six services
Calls TransactionService (avg sale price), CompetitionService (avg listing price), VehicleConditionRepository (condition score by VIN), DemandTrendService (demand index), NewCarPriceService (on-road price), and DepreciationService (depreciation %) — all in sequence, each hitting MongoDB.
5
Weighted price is computed
The six factor values are combined using the weighted algorithm (see Prediction engine section). A confidence score is also produced based on how many data points were available.
6
PricePredictionResponse is returned as JSON
Contains predictedPrice, priceRangeLow (−10%), priceRangeHigh (+10%), confidenceScore, and a factors object showing every raw input value used.

Algorithm

Prediction engine

The prediction algorithm runs in two stages: a weighted base price from three market sources, then two sequential multiplier adjustments.

Stage 1 — weighted base price

Past transaction average
40%
Competition listing average
30%
New car price × (1 − depreciation%)
20%
⚠️
Missing data handling

If a data source has no records for the requested make/model/year, its weight is excluded from the sum. A car with only transaction data still gets a valid prediction at reduced confidence.

Stage 2 — multiplier adjustments

Condition multiplier

Applied when a VIN is supplied and a condition record exists. Formula: 0.85 + (conditionScore / 10.0) × 0.30. A score of 0 applies 0.85× (15% penalty); a score of 10 applies 1.15× (15% premium).

Demand multiplier

Applied when demand trend data exists. Formula: 0.90 + (demandIndex / 100.0) × 0.20. A demand index of 0 applies 0.90×; an index of 100 applies 1.10×.

Confidence score

Transaction data present+40 points
Competition data present+30 points
Condition score present+20 points
Base (always)+10 points

Testing strategy

Service unit tests — ServiceTests.kt

Pure unit tests. MockK replaces every repository with a fake so no Spring context starts. Tests run in milliseconds.

@ExtendWith(MockKExtension::class)
class TransactionServiceTest {

    @MockK lateinit var repo: TransactionRepository
    @InjectMockKs lateinit var service: TransactionService

    @Test
    fun `getById should throw when not found`() {
        every { repo.findById("bad-id") } returns Optional.empty()
        assertThrows<NoSuchElementException> { service.getById("bad-id") }
    }
}

Controller slice tests — ControllerTests.kt

@WebMvcTest loads only the web layer (controllers + exception handler). MockMvc fires real HTTP requests in-process without a running server or database.

@WebMvcTest(TransactionController::class)
@Import(TransactionControllerTest.MockConfig::class)
class TransactionControllerTest {

    @Test
    fun `POST transaction with invalid body should return 400`() {
        val invalidReq = TransactionRequest(make = "", /* ... */)
        mockMvc.perform(post("/api/v1/transactions")
            .contentType(MediaType.APPLICATION_JSON)
            .content(objectMapper.writeValueAsString(invalidReq)))
            .andExpect(status().isBadRequest)
            .andExpect(jsonPath("$.errors").isArray)
    }
}

Quality

CI/CD pipeline

The GitHub Actions workflow at .github/workflows/ci.yml runs on every push and pull request to main and develop.

1
Checkout code
actions/checkout@v4 fetches the full repository at the pushed commit.
2
Set up JDK 17 (Temurin)
actions/setup-java@v4 with Gradle caching — subsequent runs skip dependency downloads.
3
Build (./gradlew build -x test)
Compiles all Kotlin sources. If compilation fails the pipeline stops here.
4
Run all tests (./gradlew test)
Runs all unit and slice tests. Uses the embedded flapdoodle MongoDB — no external database needed in CI.
5
Generate JaCoCo coverage report
Produces HTML and XML reports. The HTML artifact is uploaded so you can download and inspect it from the GitHub Actions run page.
6
Enforce 70% coverage threshold
./gradlew jacocoTestCoverageVerification fails the build if instruction coverage drops below 70%. This blocks merging PRs that delete or skip tests.
